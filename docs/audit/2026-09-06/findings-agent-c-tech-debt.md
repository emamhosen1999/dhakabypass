## 1. Verdict

- **The single biggest structural liability is that the entire legacy site — 5,225 lines across 11 route files under `app/(site)/` — is already dead code, and nothing in the repo admits it.** Nine `permanent: true` redirects at `next.config.mjs:134-144` intercept every unprefixed legacy path before the filesystem router is consulted, and the `beforeFiles` rewrite at `next.config.mjs:130` takes `/`. Not one route in `app/(site)/` can be reached. Meanwhile four separate files still contort themselves around the fiction that it is live.
- **Worse: those nine redirects are uncommitted.** `git diff` shows `next.config.mjs` with +19 lines in the working tree only; `git log -S "'/economic-impact', '/en/project'" -- next.config.mjs` returns nothing. The URL contract of a live public site exists solely in one developer's working copy, alongside an untracked 258 KB `db/sql/03-content-recovery.sql` and an untracked `scripts/apply-content-recovery.mjs` that the (also-modified) CI workflow already invokes at `.github/workflows/production-release.yml:46`. Lose that machine and you lose the release.
- **The code quality is genuinely high and the documentation is systematically false.** Every server action is authorization-gated, the upload path is properly hardened, SQL uses placeholders everywhere with clamped `LIMIT` interpolation, and 752 tests pass. But `lib/seo/routes.js:7-40`, `next.config.mjs:39-46`, `app/robots.js:42-45`, `components/chrome/DocumentLang.jsx:13-22`, `middleware.js:7-9` and `docs/deployment/2026-09-04-deploy-runbook.md:263` all assert as load-bearing fact something the code now contradicts. These are not stale asides — they are the stated *justification* for a report-only CSP, a JS-dependent accessibility hack, and a post-deploy check that would now fail.
- **Dependencies carry an unpatched RCE.** `npm audit --omit=dev` reports 7 vulnerabilities, 3 critical, against `next@15.2.3` (including GHSA-9qr9-h5gf-34mp, RCE in the React flight protocol, and GHSA-w37m-7fhw-fmv9, Server Actions source-code exposure) and `@auth/core` (OAuth state/PKCE cookies not bound to their provider). 15.2.3 was the CVE-2025-29927 patch and has been superseded many times over.
- **There is no CI.** `.github/workflows/production-release.yml:2-3` is `on: workflow_dispatch` and nothing else. No push trigger, no PR trigger. `npm test` runs only when a human manually clicks "run workflow" to cut a production release. There is no linter, no formatter, no `tsconfig`, no `jsconfig`, and no `lint` script anywhere — 22,281 lines of JS/JSX with zero static analysis.
- **There are no error boundaries.** Not one `error.jsx` or `global-error.jsx` exists in `app/`. Data reads degrade beautifully (every repo catches and returns `[]`), but any uncaught throw in a render path gives the visitor Next's raw "Application error: a server-side exception has occurred" on a government-linked infrastructure site. Total observability is three `console.error` calls.

## 3. Security findings

**S1 — `next@15.2.3` carries an RCE advisory. Exploitable: unknown, treat as yes.**
`npm audit --omit=dev` lists 13 advisories against the installed version, including *"Next.js is vulnerable to RCE in React flight protocol"* (GHSA-9qr9-h5gf-34mp), *"Next Server Actions Source Code Exposure"* (GHSA-w37m-7fhw-fmv9), *"Next.js: HTTP request smuggling in rewrites"* (GHSA-ggv3-7p47-pfv8 — and this app uses `rewrites()` at `next.config.mjs:127-131` plus a host-based rewrite in `middleware.js:30`), and *"Improper Middleware Redirect Handling Leads to SSRF"* (GHSA-4342-x723-ch2f). Attack: a crafted RSC/flight payload POSTed to any route. The site runs Server Actions on every admin screen and on the public contact form, so the flight endpoint is reachable unauthenticated at `/en/contact`. 15.2.3 was released solely to patch CVE-2025-29927; everything since is unpatched here. **Upgrade is the whole fix and `npm audit fix` names `next@15.5.25`.**

**S2 — `@auth/core <=0.41.2` OAuth state/nonce/PKCE cookies are not bound to their provider. Exploitable: yes, if Google OAuth is enabled.**
GHSA-x445-f3h2-j279. Google is conditionally enabled at `auth.js:74`. The attack is a provider-confusion login CSRF: an attacker initiates a flow with one provider and completes it against another using the unbound state cookie. Mitigated in depth here — `auth.js:89-91` re-checks `isAllowedAdmin(user.email)` for **every** provider, and `jwt()` at `:93` re-derives `isAdmin` from `ADMIN_EMAILS` on every request — so a successful confusion still lands on an email that must be on the allowlist. Real but not catastrophic. Also in the same advisory set: `getToken()` throws uncaught on a malformed `Bearer` header (GHSA-xmf8-cvqr-rfgj) — an unauthenticated 500 on any NextAuth route.

**S3 — Role check missing on the legacy upload endpoint. Exploitable: yes, by an authenticated translator.**
`app/admin/api/upload/route.js:28-31` gates on `session?.user?.isAdmin` alone. Its sibling `app/admin/api/media/route.js:11,20` correctly requires `can(session.user.role, 'manage_media')`. A user with role `translator` — whose permission set is exactly `['translate']` per `lib/auth/roles.js:7` — can POST an 8 MB file, have it persisted, and have a `gallery_images` row inserted (`:66-71`) publishing it to the site. `tests/unit/admin-legacy-guards.test.js:34-38` asserts translators are denied `manage_media` on every *server action*; the API route was never in that list. Fix is two lines.

**S4 — No rate limiting on any public write path. Exploitable: yes, trivially.**
`app/[locale]/contact/actions.js` has a honeypot (`:32`) and nothing else. `app/admin/actions.js:148` (contact) and `:181` (newsletter) have neither. A script can insert unbounded rows into `contact_messages` and `newsletter_subscribers` on a shared-host MySQL with a disk quota. `contact_messages` is exactly the table the runbook has no rollback for. The clipping at `app/[locale]/contact/actions.js:46,53` bounds row *width* (191/255 chars) but `message` is `longtext` and unbounded — a single request can store megabytes.

**S5 — Report-only CSP on a justification that is no longer true. Exploitable: not directly; it removes a defence.**
`next.config.mjs:39-46` explains that the enforcing CSP is withheld from everything outside `/`, `/en|bn|zh/*` and `/admin/*` because *"The legacy site at `app/(site)/` is LIVE… it embeds third-party iframes… A Content-Security-Policy strict enough to be worth having would break those embeds."* The redirects seventy lines below in the same file make every one of those pages unreachable. The report-only header at `:124` now applies to essentially nothing but 404s and `/uploads/*`. The enforcing policy should be promoted to `/:path*` — it costs nothing and removes a permanent asterisk. Separately, `script-src 'unsafe-inline'` (`:78`) is justified at `:51-57` by *"`middleware.js` is on the do-not-modify list, so that [nonce] route is closed"* — a self-imposed policy, not a technical constraint, and `git log -- middleware.js` shows the file has one commit and is not externally owned.

**S6 — Upload and file-serving path: clean.** Stated for completeness because it is the usual disaster area and is not one here. `lib/media.js:57-91` derives the stored extension *only* from a validated MIME allowlist (`:40-47`) and never from the client filename, writes with `flag: 'wx'` so a name is never silently overwritten, and unlinks the file if the DB insert fails (`:106`). `app/uploads/[...path]/route.js:41-51` resolves against `path.resolve(uploadRoot())` and rejects anything outside it including the `root + sep` boundary case, sets `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`, and forces `Content-Disposition: attachment` on `.svg` (`:77-79`) — which is what makes keeping SVG in the allowlist defensible. Size is checked twice, on the declared `file.size` and again on the actual buffer (`app/admin/api/upload/route.js:42,58`). No traversal, no unrestricted type, no SVG-XSS.

**S7 — Authorization coverage: complete, verified action by action.** All 10 server-action modules carry `'use server'` and call `assertCan(...)` as the first statement of every exported action: `app/admin/actions.js:38,77,95,122,133,204,263`; `corridor/actions.js:27,35,54,63,89,98,128,137,159,168`; `corridor/traffic-actions.js:10` (shared wrapper); `media/actions.js:45,116`; `menus/actions.js:31,83,109`; `news/[id]/translations/actions.js:23,69`; `pages-v2/actions.js:13,18,57`; `pages-v2/[id]/block-actions.js:19,37,51,65,88`; `redirects/actions.js:20,62`; `settings/actions.js:27`. The only unguarded exports are the two intentionally-public ones (`submitContactAction`, `subscribeNewsletterAction`). `lib/auth/assert-can.js:11-15` correctly documents *why* it is not itself in a `'use server'` module. Nothing relies on middleware — `middleware.js:7-9` says so, though it names the wrong file (the guard is `app/admin/(dash)/layout.jsx:32-33`, not `app/admin/layout.jsx`, which is a bare `<div>` at `:14-16`). CSRF is handled by Next's built-in Server Action origin check; no custom mutation endpoints bypass it.

**S8 — Secrets: clean.** `.env.local` is untracked; `.gitignore:8` covers `.env*.local`. `.env.example` has empty values for `DB_PASSWORD`, `AUTH_SECRET`, `AUTH_GOOGLE_SECRET`, `ADMIN_PASSWORD`, `TOMTOM_API_KEY`. `db/sql/README.md:61-68` explicitly excludes `users`, `contact_messages` and `newsletter_subscribers` rows from the generated seed, for the right reasons.

## 6. Deploy & migration risk

The deploy model is documented well (`docs/deployment/2026-09-04-deploy-runbook.md`, 311 lines) and the guardrails in `scripts/release-to-branch.mjs` are real: it refuses an artifact built with no `SITE_URL` (`:123`), from a dirty tree (`:135`), on a non-Linux platform (`:142`), or targeting production without `--yes` (`:152`). That is more rigour than most projects have. The risk is entirely in the parts that are still human.

**The manual steps, and what breaks when one is skipped:**

1. **Regenerate the SQL** (`npm run db:sql`, runbook line 201). *If skipped:* `db/sql/*.sql` drifts from `scripts/db-setup-v*.mjs`. The generator does verify itself (imports twice into a scratch DB and compares row counts, `db/sql/README.md:29-32`) — but only when someone runs it. Nothing in CI checks that the committed SQL matches the migration chain.
2. **Import the changed SQL in phpMyAdmin, after an Export backup** (runbook line 237). *If skipped:* the app boots against a schema missing a column and fails at the first query touching it — as a 500 with no error boundary (D7) and no log (D8). **This is the single most dangerous step in the project.** There is no migration runner on the host, no applied-migrations table, no way to ask the database what version it is at.
3. **Apply a schema *upgrade* by hand-copying an `ALTER` out of a `.mjs` file** (`db/sql/README.md:83-87`). `01-schema.sql` is `CREATE TABLE IF NOT EXISTS` only — it cannot upgrade an existing database. So the operator must open the right `db-setup-v*.mjs`, find the right `ALTER`, and paste it. Six such migrations exist today; there will be more. *If skipped or mis-transcribed:* silent data corruption or a missing column, with a phpMyAdmin export as the only rollback.
4. **Import `03-content-recovery.sql` after the first two** (`db/sql/README.md:14`). This file is **currently untracked** (D1). On a fresh install from `main` as committed, it does not exist.
5. **Build on Linux** (runbook line 217) — `sharp`'s native bindings are traced into the standalone artifact. Enforced by `release-to-branch.mjs:142`, so this one is actually safe. But it means the Windows dev machine cannot cut a release: **CI is the only production path**, and CI is manual-dispatch-only (D6).
6. **Run `node preflight.mjs` on the server before `touch tmp/restart.txt`** (runbook line 227). Well-designed — checks the environment without booting. Nothing enforces it.
7. **Post-deploy verification step 7 is now wrong** (D10). It instructs the operator to confirm all nine legacy URLs return 200. They return 308.

**Rollback.** The site rollback is genuinely good: `git reset --hard <previous release>; touch tmp/restart.txt` (runbook line 275), and it works because the artifact — including `node_modules/` and `.next/` — is complete in git. **The database has no rollback.** The runbook says so plainly at line 292: *"There is no automatic rollback and nothing in this project creates one. The only restore point is a phpMyAdmin Export taken before the import."* If someone skips the export and the import goes wrong, the recovery path is whatever the host's own backup retention happens to be.

**Reproducibility.** The build is close to reproducible — `npm ci` with a committed `package-lock.json`, pinned Node `22.23.2` (`.github/workflows/production-release.yml:36`), pinned `mariadb:11.4`. The gap is that CI seeds its build database by running seven scripts in sequence (`:41-47`), one of which (`apply-content-recovery.mjs`) is untracked, and the build bakes `unstable_cache` entries warmed against that database into `.next/cache` — which `lib/content/cache.js:26-42` documents as having already caused a production incident, and mitigates with a 300-second recovery floor rather than by not doing it.
